## Shared Core link contract

A product is “linked” to the ecosystem only when the link is explicit and governed.

Allowed shared concepts:
- identity / role patterns;
- organisation, tenant and site isolation;
- RED / AMBER / GREEN / HOLD operational state;
- accountable action ownership, due dates and escalation;
- evidence references and closure;
- append-only/auditable event patterns;
- integration health and fail-closed bridges;
- configuration registry;
- reporting/evidence packs;
- retention/deletion/privacy control patterns.

A link does **not** authorise:
- direct cross-product customer database joins;
- shared customer secrets;
- silent data copying;
- clinical/statutory/tactical/emergency authority;
- customer data becoming ON TRACK portfolio data;
- Revenue Rescue becoming a Shared Core dependency.

## Repository cleanup disposition

Physical repository deletion is **not** the cleanup strategy. Historical repositories containing unique provenance remain reference records. The cleanup rule is:
1. route every repository to one family;
2. nominate canonical runtime(s);
3. mark aliases/precursors historical;
4. prevent new development in historical aliases;
5. archive/delete only after provenance/blob/reference checks and repository-admin authority are available.

## New-product rule

Before creating another repository, first decide:
- extension of an existing product;
- configuration of an existing command centre;
- reusable Shared Core capability;
- genuinely standalone commercial product.

This prevents the portfolio from fragmenting again.

## Portfolio link acceptance

The businesses are considered ecosystem-linked when:
- their canonical home is named;
- reusable capabilities point to Shared Core rather than copied engines;
- isolation boundaries are explicit;
- cross-product bridges are versioned, minimum-necessary, revocable and fail closed;
- commercial status is accurately labelled;
- historical repositories are routing/provenance records rather than competing sources of truth.
